تحليل مشاكل الواجهة والأدوات التفاعلية (Frontend Auditing)

1. مودال إضافة مفتاح API فارغ بالكامل (Empty Add Key Modal Placeholder)
حرِج جداً - Critical UI Defect

عند النقر على زر "Generate New API Key" أو إضافة مفتاح، يفتح مودال #addKeyModal في الملف resources/views/hubs/partials/ai-hub/api-keys/modals/add-key.blade.php الذي يحتوي على نص تجريبي مؤقت:

<p class="text-muted text-center py-5"><i class="fa-solid fa-wand-magic-sparkles fa-2x mb-3 opacity-50"></i><br>Wizard steps would go here.</p>
السبب والأثر: عدم وجود مدخلات لاختيار المزود، اسم المفتاح، النص المشفر، تاريخ الانتهاء أو زر الحفظ الحقيقي، مما يمنع المستخدم تماماً من إضافة أي مفتاح جديد من الواجهة!
2. أخطاء JavaScript في الداش بورد (Dashboard Telemetry Syntax/Fetch Exception)
حرِج - JS Runtime Crash

في الملف resources/views/hubs/partials/ai-hub/dashboard/index.blade.php، عند جلب بيانات الـ Telemetry عبر fetch('/hub/models/telemetry') يحدث خطأ غير معالج عند فشل الاستجابة أو إرجاع 500 HTML error:

Uncaught (in promise) SyntaxError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
السبب والأثر: غياب try...catch ومكونات الـ Fallback في جافاسكريبت مما يسبب توقف رسم Chart.js وظهور رسائل خطأ في المتصفح.
3. إدخال شروط التوجيه (Intent Routing Conditions) كـ Text Raw JSON
متوسط - UX Flaw

يُطلب من المستخدم كتابة مصفوفة الشروط (مثل الحد الأقصى للتكلفة أو التوكنات) كـ JSON نصي مباشر في فورم الإضافة، مما يسبب أخطاء تنسيق وتجربة استخدام صعبة.

4. غياب التحديث الحي عبر WebSockets (Top Health Ribbon & Live Counters)
متوسط - Missing Realtime

عدادات الـ TPM والـ Active Requests وشريط الصحة في أعلى الصفحة غير مرتبطة بـ Echo Channels/Reverb المباشرة وبالتالي لا تتحدث إلا عند إعادة تحميل الصفحة.

تحليل مشاكل الباك إند ومحرك التراجع المتعدد (Multi-Provider Fallback)

كيف يعمل الـ Fallback حالياً؟ وهل يمكن إضافة أكثر من Provider؟

حالياً، موديل IntentRouting.php وقاعدة البيانات يحتفظان بـ fallback_provider_id واحد فقط ومزود افتراضي واحد لكل غرض (Intent). عند فشل الطلب على المزود الرئيسي عبر CircuitBreaker.php أو IntentRoutingEngine.php يتم التحويل إلى المزود الاحتياطي الفردي المسجل.

الوضع الحالي: Default Provider (OpenAI) ──(فشل)──► Single Fallback Provider (Gemini)
الوضع المطلوب لتعدد الـ Fallbacks: Default Provider (OpenAI) ──► Fallback #1 (Gemini) ──► Fallback #2 (Groq) ──► Fallback #3 (Local Ollama)

النتيجة: النظام الحالي ينفذ Fallback أحادي بكفاءة، ولكن لدعم سلسلة تراجع متعددة (Multi-Provider Fallback Chain) يتطلب تغيير حقل fallback_provider_id في الداتا بيز إلى fallback_chain (json array) وتحديث خوارزمية الدوران في UniversalAiGatewayService.php.

1. تعارض أسماء الأعمدة وحقول التاريخ (Column Inconsistency in Usage Logs)
حرِج - Database & Query Bug

في ملف Migration لجدول usage_logs العمود هو timestamp مع وجود Index عليه، بينما في الكلاس AiHubService.php الدالة getTelemetry() تقرأ الحقل بـ created_at مما يسبب تباطؤاً وفشل بعض الاستعلامات عند التحليل.

2. غياب الـ Streaming (Server-Sent Events)
ميزة مفقودة - Streaming Lack

محول REST العام DynamicRestProvider.php لا يدعم الـ Stream Response المباشر توكن بتوكن، بل ينتظر الرد الكامل من الـ LLM API.

حالة المفاتيح والتدوير وتقارير الاستهلاك لكل مفتاح

المكون / الميزة الحالة الحالية المشكلة / النقص المطلوب لتجهيزه
إضافة وتشفير المفاتيح معطل من الواجهة مودال الإضافة مفرغ في الواجهة (Placeholder)، بينما الباك إند مشفر بـ AES-256. بناء مدخلات المودال وتوصيله بـ storeApiKey.
التدوير التلقائي (Key Rotation) جزئي - غير مجدول الأمر ai-hub:rotate-keys موجود ولكنه غير مضاف لـ Laravel Scheduler. إضافة الأمر لـ routes/console.php للتفعيل اليومي.
فحص صحة المفتاح المنفرد غير موجود الفحص يتم للمزود بالكامل وليس لكل مفتاح بشكل منفرد (Ping Key). إضافة زر Test Key ونقطة نهاية بفحص اتصال كل مفتاح.
تقارير الاستهلاك لكل مفتاح مفقود في الـ Schema جدول usage_logs لا يحتفظ بـ api_key_id لربط التكلفة بالمفتاح. إضافة Migration بـ api_key_id وتحديث التتبع.
فترة التبريد (Cooldown Multiplier) ثابتة فترة التبريد عند أخطاء 429 ثابتة ولا تتضاعف مع تكرار الأخطاء. تطبيق خوارزمية Exponential Backoff.
